# Portfolio Chat: Context-Aware Dashboard Popup

## Goal

Replace the temporary `/dashboard/chat` learning page with one basic, polished chat popup available on both `/dashboard` and `/dashboard/[walletId]`.

The chat should use the current route as optional context rather than as a hard access boundary:

- `/dashboard` has no default wallet
- `/dashboard/[walletId]` uses the wallet from the URL as the default wallet
- the user can explicitly ask about a different wallet from either route

Keep the implementation intentionally small:

- one shared chat API
- all AI provider, prompt, tool, and streaming configuration kept in `src/app/api/chat/route.ts`
- one shared popup UI
- two read-only tool types
- no persisted conversations
- no chat history API
- no rate limiting
- no automated tests

## Final decisions

### Conversation lifetime

Conversation state exists only in client memory.

Behavior:

- closing and reopening the dialog on the same route preserves the current conversation
- changing from `/dashboard` to `/dashboard/[walletId]` resets the conversation
- changing from one wallet route to another resets the conversation
- refreshing the page resets the conversation
- no messages or conversations are saved in the database

Use a scope key only to control component lifetime:

```ts
chatScope = currentWalletId
  ? `wallet:${currentWalletId}`
  : "dashboard"
```

This is not a persisted `conversationId`.

### Route context semantics

Treat the wallet from the URL as a default, not as a strict boundary.

```ts
type ChatContextInput = {
  currentWalletId?: string;
};
```

Examples:

- on `/dashboard`, “What positions do I have?” has no default wallet
- on `/dashboard/abc`, “What positions do I have?” means wallet `abc`
- on `/dashboard/abc`, “What positions are in my Retirement wallet?” may target a different wallet

`currentWalletId` is untrusted client context. It never grants access. Every wallet lookup must include `session.user.id`.

### Available tools

Expose exactly two tool types:

```ts
getWalletsOverview()
getWalletPositions({ walletId?: string })
```

Keep:

```ts
stopWhen: isStepCount(5)
```

The step count is only a safety limit. It does not change the decision to expose exactly two tool types.

### Tool naming

Rename:

```ts
getLatestWalletSnapshots
```

to:

```ts
getWalletsOverview
```

The new name describes the model-facing capability rather than the database implementation.

Rename the timestamp in the tool output:

```ts
snapshotAt -> dataAsOf
```

The assistant must not use the technical word “snapshot” when speaking to the user.

### Wallet selection rules

For questions requiring positions:

```txt
if user explicitly identifies a wallet:
  resolve that wallet and use it
else if currentWalletId exists:
  use the current wallet
else:
  call getWalletsOverview

  if wallet count is 0:
    explain that the user has no wallets
  if wallet count is 1:
    use the only wallet automatically
  if wallet count is greater than 1:
    ask the user which wallet they mean
```

Name ambiguity:

- wallet names may repeat across currencies
- if the same name matches multiple currencies, ask which currency the user means
- until database uniqueness is added separately, defensively handle duplicate `name + currency` combinations too
- never choose an ambiguous wallet arbitrarily
- keep wallet IDs internal and do not display them in assistant text or tool status UI

Changing wallet-name uniqueness rules, schema constraints, migrations, create-wallet validation, and rename-wallet validation are outside this plan.

### Meaning of tool input

The optional `walletId` in `getWalletPositions` is generated by the model, not typed manually by the user.

Use a clear executor variable name:

```ts
execute({ walletId: requestedWalletId })
```

Resolve the target with:

```ts
targetWalletId = requestedWalletId ?? context.currentWallet?.id
```

Typical flows:

```txt
Current wallet route + implicit question
  model calls getWalletPositions({})
  executor falls back to context.currentWallet.id
```

```txt
Global dashboard + named wallet
  model calls getWalletsOverview()
  model reads the internal walletId for the matching name/currency
  model calls getWalletPositions({ walletId })
```

```txt
Current wallet route + explicitly named different wallet
  model calls getWalletsOverview()
  model resolves the requested wallet
  model calls getWalletPositions({ walletId })
```

An ID supplied by the model is still untrusted and must be checked against the authenticated user.

### Position aggregation

The existing `QUERIES.getWalletPositions(walletId, userId)` returns open purchase lots. Do not expose those raw lots as the final tool result.

Aggregate them by company symbol:

```ts
type AggregatedWalletPosition = {
  symbol: string;
  companyName: string;
  quantity: number;
  averagePurchasePrice: number;
  lotsCount: number;
};
```

Aggregation pseudocode:

```txt
groups = Map keyed by companySymbol

for each open lot:
  group = groups[lot.companySymbol]
  group.quantity += lot.quantity
  group.purchaseCost += lot.quantity * lot.pricePerShare
  group.lotsCount += 1

for each group:
  averagePurchasePrice = purchaseCost / quantity
  return symbol, companyName, quantity, averagePurchasePrice, lotsCount
```

Rules:

- use remaining open `quantity`, not `initialQuantity`
- preserve full numeric precision in the tool result; presentation rounding belongs to the response/UI
- an empty array is a valid result meaning the wallet has no open positions
- do not add live price, current value, or unrealized profit/loss in this iteration

### Language and data limitations

The assistant should answer in the language of the user’s latest message.

The assistant may provide investment advice; do not add a system-level prohibition against recommendations.

The assistant must still:

- avoid inventing portfolio or market data
- clearly state when required data is unavailable
- avoid claiming that purchase prices are current market prices
- use only the two available tools for user portfolio facts
- avoid exposing tool names, schemas, wallet IDs, or implementation details

For wallet values from `getWalletsOverview`:

- return `dataAsOf` to the model
- mention the data time when answering value-related questions
- do not unnecessarily mention it when only listing positions
- explain that values may be delayed by approximately 15 minutes when relevant

### UI scope

Use a floating trigger button in the bottom-right corner and open a modal shadcn `Dialog`.

Use these shadcn components:

- existing `Dialog`
- `MessageScroller`
- `Message`
- `Bubble`
- existing `Button`

Use only the basic `MessageScroller` features:

- `MessageScrollerProvider`
- `MessageScroller`
- `MessageScrollerViewport`
- `MessageScrollerContent`
- `MessageScrollerItem`
- stable `message.id`
- `scrollAnchor` on user messages
- `autoScroll`
- `MessageScrollerButton`

Do not add:

- saved transcript opening
- prepended history
- message search
- message permalinks
- visibility tracking
- direct message jumps
- virtualization
- message animations

Use only the basic `Message` and `Bubble` composition:

- user messages aligned to the end
- assistant messages aligned to the start
- no avatars
- no headers or footers
- no copy, retry, regenerate, or feedback actions
- no attachments
- no Markdown dependency in this iteration; preserve plain-text whitespace

### Tool status UI

Do not render raw tool input or output.

Map tool parts to short status rows:

```txt
getWalletsOverview
  pending -> “Checking your wallets…”
  success -> “Wallets checked”
  error   -> “Could not check wallets”

getWalletPositions
  pending -> “Loading positions…”
  success -> “Positions loaded”
  error   -> “Could not load positions”
```

Use AI SDK tool-part states:

```txt
input-streaming / input-available -> pending
output-available                  -> success
output-error                      -> error
```

The status row may use a spinner while pending and a compact success/error icon afterward. It must never display wallet IDs or serialized payloads.

### Input behavior

Keep the composer basic:

- one controlled text input
- submit on form submission/Enter
- trim whitespace before sending
- ignore an empty value
- clear the input after a successful local submit
- disable the input and submit button while status is `submitted` or `streaming`
- show a simple pending state while waiting for initial output

Do not add:

- Stop
- Retry
- Regenerate
- message queueing
- editing previous prompts
- multiline prompt behavior
- attachments

### Error behavior

UI request/stream errors:

- render one generic inline error below the transcript
- re-enable the composer after the request reaches the error state
- do not use a toast
- do not automatically retry
- do not expose technical error text to the user

Suggested copy:

```txt
Could not generate a response. Please try again.
```

Server behavior:

- missing session -> HTTP 401
- malformed request/context -> HTTP 400
- unavailable `currentWalletId` -> generic HTTP 404; do not silently fall back to dashboard scope
- unavailable wallet requested by a tool -> structured generic tool result, without revealing whether another user owns that ID
- unexpected database/model failures -> normal failed stream/request behavior and server-side logging

### Visual direction

Keep the chat consistent with the existing portfolio dashboard and project palette:

- primary lime `#A7C72A` for the floating trigger and active states
- sage `#87B071` for hover/focus accents
- pale green `#D9E3AA` for subtle borders/backgrounds where appropriate
- forest/dark green tones for muted and primary text
- use existing semantic theme variables where they already represent these colors
- keep dark-mode support inherited from the existing theme
- make the dialog height-constrained so `MessageScroller` can fill the remaining body area
- on small screens, let the dialog use nearly the full viewport

## Runtime contracts

### Request body

Client transport sends:

```ts
type PortfolioChatRequest = {
  messages: UIMessage[];
  context: {
    currentWalletId?: string;
  };
};
```

Do not send wallet lists, wallet names, positions, user IDs, or page query results from the client.

### Resolved server context

Convert untrusted request context into a server-owned discriminated union:

```ts
type ResolvedPortfolioChatContext =
  | {
      scope: "dashboard";
      currentWallet: null;
    }
  | {
      scope: "wallet";
      currentWallet: {
        id: string;
        name: string;
        currency: string;
      };
    };
```

Resolution pseudocode:

```txt
if currentWalletId is absent:
  return dashboard context

wallet = QUERIES.getWalletById(currentWalletId, session.user.id)

if wallet does not exist:
  return generic not-found response

return wallet context using server-read id, name, and currency
```

Only the resolved context may be passed into the model/tool layer.

### `getWalletsOverview` output

Return an internal structured result:

```ts
type WalletsOverviewOutput = {
  status: "success";
  wallets: Array<{
    walletId: string;
    name: string;
    currency: string;
    totalValue: number;
    netInvested: number;
    dataAsOf: string | null;
  }>;
};
```

Rules:

- query by authenticated `userId`
- include `walletId` so the model can chain into `getWalletPositions`
- keep `walletId` hidden in visible UI
- serialize dates to ISO strings
- an empty `wallets` array is valid

### `getWalletPositions` input/output

Input:

```ts
type GetWalletPositionsInput = {
  walletId?: string;
};
```

Expected outputs:

```ts
type GetWalletPositionsOutput =
  | {
      status: "success";
      wallet: {
        name: string;
        currency: string;
      };
      positions: AggregatedWalletPosition[];
    }
  | {
      status: "wallet-selection-required";
    }
  | {
      status: "wallet-unavailable";
    };
```

Executor pseudocode:

```txt
requestedWalletId = tool input walletId
targetWalletId = requestedWalletId ?? context.currentWallet?.id

if targetWalletId is absent:
  return wallet-selection-required

wallet = QUERIES.getWalletById(targetWalletId, userId)

if wallet does not exist:
  return wallet-unavailable

lots = QUERIES.getWalletPositions(wallet.id, userId)
positions = aggregate lots by company symbol

return success with wallet name/currency and aggregated positions
```

Calling both wallet queries with `userId` is deliberate defense in depth.

## System prompt plan

Build one base prompt plus one server-generated context section.

Base behavior pseudocode:

```txt
You are the portfolio assistant for the authenticated user.
Reply in the language of the user’s latest message.
Use tools for factual claims about the user’s wallets and positions.
Never invent missing portfolio or market data.
Do not expose tool names, arguments, wallet IDs, or implementation details.
Do not use the word “snapshot” in user-facing responses.

Use getWalletsOverview for:
- listing wallets
- wallet values and invested amounts
- resolving a wallet name/currency to an internal ID

Use getWalletPositions for:
- open holdings in one selected/default wallet

Wallet choice rules:
- explicit wallet in the request overrides current route context
- otherwise use current route wallet if available
- without a current wallet, inspect available wallets
- zero wallets: explain the absence
- one wallet: select it automatically
- multiple wallets: ask for clarification
- ambiguous duplicate names: ask for currency/additional distinction

When discussing wallet values, communicate dataAsOf when relevant.
Do not imply that averagePurchasePrice is a live market price.
```

Dynamic context pseudocode:

```txt
Dashboard scope:
  “The user is currently on the general dashboard. No wallet is selected by the route.”

Wallet scope:
  “The user is currently viewing wallet {name} ({currency}). Treat it as the default wallet unless the user explicitly asks about another wallet.”
```

Generate the dynamic section only from the resolved server context, never directly from unvalidated request data.

### `src/app/dashboard/chat/chat-popup.tsx`

Make this a client component.

Responsibilities:

- read `walletId` from `useParams`
- normalize it to `currentWalletId?: string`
- derive `chatScope`
- recreate the chat session when `chatScope` changes
- keep the chat hook mounted when only the dialog closes
- configure `DefaultChatTransport` with request context
- own dialog open/closed state
- render transcript, tool statuses, errors, and composer

Important component lifetime shape:

```tsx
ChatPopup:
  params = useParams()
  currentWalletId = normalize params.walletId
  scope = currentWalletId ? `wallet:${currentWalletId}` : "dashboard"

  return ChatSession(
    key = scope,
    currentWalletId = currentWalletId
  )
```

`ChatSession` should call `useChat` outside the conditionally mounted dialog content:

```tsx
ChatSession:
  chat = useChat(transport with context.currentWalletId)
  open = local dialog state

  return Dialog(open):
    floating trigger
    conditional dialog content using chat state
```

This lifetime is required because Radix Dialog content may unmount when closed. If `useChat` were placed inside `DialogContent`, closing the dialog would accidentally erase the conversation.

Transport pseudocode:

```ts
transport = new DefaultChatTransport({
  api: "/api/chat",
  body: {
    context: { currentWalletId },
  },
});
```

Composer pseudocode:

```txt
isBusy = status is submitted or streaming

onSubmit:
  prevent default
  text = input.trim()
  if text is empty or isBusy:
    return
  sendMessage({ text })
  clear local input
```

Transcript pseudocode:

```tsx
MessageScrollerProvider(autoScroll):
  MessageScroller:
    MessageScrollerViewport:
      MessageScrollerContent:
        for each message:
          MessageScrollerItem(
            messageId = message.id,
            scrollAnchor = message.role is user
          ):
            Message(align based on role):
              MessageContent:
                for each part:
                  text part -> Bubble with whitespace-preserved text
                  known tool part -> ToolStatusRow
    MessageScrollerButton
```

Do not render raw reasoning parts, tool inputs, tool outputs, or unknown implementation payloads.

### `src/app/api/chat/route.ts`

Keep the complete portfolio-chat server implementation in this route. Do not introduce a separate AI provider, chat configuration, or tool module.

Move the existing Groq provider initialization from `src/server/ai/groq.ts` into this route, then delete `groq.ts`. Everything needed to understand and configure this chatbot should live in `route.ts`:

- Groq provider initialization and API-key configuration
- request and resolved-context types/schemas
- authentication and request parsing
- trusted route-context resolution
- position-lot aggregation
- both tool definitions and executors
- the complete system prompt and dynamic context section
- model/provider options
- message validation/conversion
- `streamText` orchestration
- UI message stream response creation

Suggested route-local helpers:

```ts
resolvePortfolioChatContext(...)
aggregateWalletPositions(...)
buildPortfolioChatSystemPrompt(...)
```

Keep the two tool definitions close to the `streamText` call so the complete model contract can be understood from one file. Avoid adding factories or abstractions whose only caller would be this route.

Route pseudocode:

```txt
POST(request):
  session = getSession()
  if no session:
    return 401

  rawBody = request.json()
  parsedBody = validate messages + context shape
  if invalid:
    return 400

  context = resolvePortfolioChatContext(
    parsedBody.context,
    session.user.id
  )
  if unavailable current wallet:
    return generic 404

  groq = initialize route-local Groq provider
  systemPrompt = buildPortfolioChatSystemPrompt(context)

  tools = {
    getWalletsOverview: tool bound to session.user.id,
    getWalletPositions: tool bound to session.user.id and context
  }

  validatedMessages = validate/convert parsedBody.messages

  result = streamText({
    existing Groq model and provider options,
    systemPrompt,
    tools,
    stopWhen: 5 steps,
    validatedMessages
  })

  return UI message stream response from result
```

Preserve the existing model/provider settings unless implementation reveals an incompatibility:

```txt
model: groq("openai/gpt-oss-20b")
reasoningFormat: hidden
reasoningEffort: low
stopWhen: isStepCount(5)
```

Remove the temporary `onStepEnd` raw `console.log(toolResults)` because it can log private portfolio payloads and was only useful during learning/debugging.

### General dashboard

```txt
Given multiple wallets
When the user asks “What positions do I have?”
Then the assistant asks which wallet they mean
```

```txt
Given exactly one wallet
When the user asks “What positions do I have?”
Then the assistant selects that wallet without unnecessary clarification
```

```txt
Given no wallets
When the user asks about positions
Then the assistant explains that no wallets are available
```

```txt
Given a uniquely named wallet
When the user names it in the question
Then the assistant resolves it through getWalletsOverview and loads its positions
```

```txt
Given the same wallet name in PLN and USD
When the user names it without currency
Then the assistant asks which currency they mean
```

### Wallet dashboard

```txt
Given /dashboard/abc
When the user asks an unqualified question about “my positions”

```

```txt
Given /dashboard/abc

```

